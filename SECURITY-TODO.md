| Priority | Risk | State | Closing test |
|---|---|---|---|
| P0 | Offline recovery trust is not bootstrapped until the maintainer supplies and commits `recovery-cosign.pub`. Hosts installed before that transition cannot use the automated recovery path. | Blocked on offline key custodian; no private material may enter this repository, GitHub, or Codex. | Both variants boot with active and recovery `keyPaths`; ephemeral active and recovery signatures each pass independently; unrelated and unsigned images fail. |
| P0 | Planned and incident signing-key rotation has not yet completed the VM/fleet-evidence rehearsal. | The disposable-registry old/next/recovery/fresh/unrelated matrix passed locally on 2026-08-05 with cosign v3.0.6; transition and incident boot evidence remain outstanding. | A transition then incident-recovery image each pass both hosted VM legs, and recorded host evidence proves the transition was booted before signer replacement. |
| P1 | Hosted CI has no physical NVIDIA GPU, so it cannot prove module loading against hardware, `nvidia-smi`, CDI device creation, or a rootless GPU workload. | Deferred pending an approved NVIDIA runner or hardware canary. | Complete the checks in [docs/hardware-canary.md](docs/hardware-canary.md) for every candidate NVIDIA release and attach the result to the release run. |
| P2 | Cosign v3.1.x removed explicit legacy key-attachment selection and auto-selects coexisting keyless attestation bundles, so active-key verification fails. | Held at live-tested v3.0.6 through Renovate until upstream behavior or host policy changes. | A newer checksum-verified cosign signs and verifies both live variants, and `sigstoreSigned` host-policy tests accept the resulting attachment while rejecting unsigned/unrelated images. |
| P2 | Keyless image signing could reduce long-lived online key exposure, but changes identity and recovery assumptions. | Evaluate separately; no migration decision made. | Threat-model review plus a rehearsal proving identity constraints, offline recovery, host policy compatibility, and rollback. |
| P2 | `opencode.yml` runs the third-party `anomalyco/opencode/github` action pinned to a hand-reviewed dev-branch commit (2026-08-05). Renovate cannot track a branch-commit pin, so it never updates: upstream fixes and security patches do not arrive, and nothing prompts a re-review — the pin drifts from upstream silently. | Accepted for now: the action executes only behind the workflow's two trust gates (maintainer-only command, same-repository PR), with read-only permissions and the API key scoped to the final step. | Upstream cuts tagged releases and the pin moves to a Renovate-tracked release SHA; until then, each re-pin is a dated, hand-reviewed commit recorded in the workflow comment. |
